I'm building a story data extraction tool for the Infinite Worlds Architect Plugin — a Claude Code plugin for the Infinite Worlds interactive fiction platform (https://infiniteworlds.mywikis.wiki/wiki/Main_Page).

## The Problem

The plugin has a `sequel-world` command that creates a sequel world configuration from an original world JSON + a story export (the text log of a played story, which can be hundreds of turns long). Currently, the agent is told to "read the ENTIRE export" and then propose field values one-by-one for the sequel world. This fails badly at scale — the agent hallucinates details, fabricates character descriptions, invents terminology, confuses characters, and over-indexes on recent events while losing early story details.

I want to build a **programmatic extraction tool** (no LLM calls — pure deterministic parsing) that pre-processes the story export into structured JSON that the agent can reference instead of consuming the raw story text. This tool will be an MCP tool in the plugin's existing MCP server (`index.js`).

## Constraints

1. **Programmatic only.** No LLM calls, no NLP libraries, no external APIs. Pure Node.js text parsing. The tool must work offline with zero dependencies beyond what's already in the plugin.
2. **Must generalize across world types.** The example exports span modern urban fantasy, psychological thriller, superhero/crime, and dark fantasy RPG. Some have extensive tracked items, some have none. Your solution must handle all of them.
3. **Be honest about what's parseable.** Don't design a schema with fields that a deterministic parser can't actually populate. Read the exports carefully and note what's structured data vs. what's unstructured prose. If something can't be extracted programmatically, say so — don't include it in the schema.
4. **Optimize for agent accuracy.** The output should help the agent propose accurate sequel world field values. Think about what data the agent actually needs at each step of the sequel-world walkthrough, and design the output to serve that workflow.
5. **Token efficiency matters.** The agent shouldn't have to load the entire extraction into context at once. Consider how the output could be structured so the agent loads only what it needs for the current field.

## What I Want From You

1. **Analyze the exports.** Read all four and build a comparison table of what structural elements are present across them. Note what's consistently available vs. what varies.
2. **Design the extraction schema.** Based on what you can ACTUALLY parse, design the JSON output format. Show a concrete example using at least two of the real exports.
3. **Design the parser.** Describe the parsing approach — state machine, regex patterns, section detection, etc. Address the delimiter collision problem (what if narrative text contains strings that look like section markers?).
4. **Design the output structure.** Single file? Multiple files? Directory? Think about how the agent consumes this data during the field-by-field walkthrough.
5. **Design agent consumption.** How does the agent use this data? Does it need query tools? A reference doc? Both?
6. **Adversarial review.** What are the failure modes? Where does this approach fall short? What can't it do that an LLM-based approach could?
7. **Refinement.** Based on the adversarial review, refine the schema and parser design to mitigate as many failure modes as possible.
